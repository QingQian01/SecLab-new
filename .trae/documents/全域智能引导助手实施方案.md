# 全域智能引导助手实施方案

## Context（为什么做这件事）

当前 SecLab 平台已有 Dify Agent + RAG（云端）、`docker-service` (Kotlin/Spring Boot, 8087) 和 `ai-agent-service` (Python/FastAPI, 8010) 两套后端，前端 `FloatingChat.vue` 通过 SSE 接 `/api/chat` 拿到 Dify 的回复。但是：

1. `docker-service` 仍用 `ProcessBuilder("docker", ...)` 调 CLI，未用 `build.gradle.kts` 里已声明的 `docker-java` SDK，无法实时订阅容器日志。
2. 学生在靶场陷入"无效试错"（重复报错、重复同一条命令、长时间卡住）时，系统不会主动介入；必须学生自己点"提示"。
3. 前端没有 TTY/错误日志的实时旁路监听通道，AI 助手对学生当前操作一无所知。

本方案构建 **"数据拦截 → 状态评估 → 动态反馈"** 闭环：docker-service 用 Docker SDK 实时订阅容器 TTY/日志 → 用挫败指数规则识别无效试错 → 把"报错切片 + 当前靶机任务"作为信号 POST 给 ai-agent-service（FastAPI 中枢）→ ai-agent-service 把信号注入 Dify `inputs` 字段，复用云端 RAG 生成启发式诊断 → 经 SSE 推送给前端 `FloatingChat`，以"AI 主动提示"形式实时渲染。

**关键约束（来自评审与用户确认）**：
- 用户已确认：WS TTY 监听放在 docker-service (Kotlin)，完整三阶段闭环。
- Dify 调用 + RAG 在云端处理，本地只负责信号组装与 SSE 转发。
- 复用现有 5 张表（`error_event`、`container_command_event`、`ai_conversation`、`ai_message`、`ai_context_injection`），**不新增表**，仅扩展若干 `source`/`context_type` 枚举值。

5. **`TtyLogStreamService.kt`** — 实时日志订阅中枢。
   - 内部 `ConcurrentHashMap<String, FramedLogsStream>`，key=containerName。
   - `FramedLogsStream` 持有 `CopyOnWriteArraySet<Sink>` + 单线程 `ExecutorService`（`Executors.newSingleThreadExecutor` per container，避免阻塞 WS handler 线程池 — 评审 Q6）。
   - `subscribe(containerName, sink)`：若该容器首次订阅，启动 `logContainerCmd().withFollowStream(true).withTailAll().withStdOut(true).withStdErr(true).exec(callback)`，callback 在该容器单线程上跑，每行通过 `sink.onNext(frame)` 推给所有订阅者；同时把行送入 `FrustrationTracker.observe()`。
   - `unsubscribe(containerName, sink)`：从 set 移除；set 空时关闭 callback + shutdown 单线程 + 从 map 移除。
   - 容器 die 事件：订阅 `dockerClient.eventsCmd().withFilter("container","die")` 异步监听，对应 containerName 主动清理订阅（评审缺口 6 补充）。

6. **`WebSocketConfig.kt`** — `@Configuration implements WebSocketConfigurer`，注册 `TtyLogHandler` 到 `/ws/tty/{containerName}`。

7. **`TtyLogHandler.kt`** — `TextWebSocketHandler`。
   - `afterConnectionEstablished`：从 URI 提取 `containerName`，从 query string 提取 `lab_session_id` / `user_id`（评审缺口 4 修复），校验 `LabAllowlist.isAllowed`，调用 `TtyLogStreamService.subscribe`。
   - `handleTextMessage`：忽略客户端→服务端文本（仅服务端→客户端推送），或支持 `{"type":"ping"}` 心跳。
   - `afterConnectionClosed`：**try/finally** 调用 `unsubscribe`（评审缺口 6 修复）。
   - 推送帧格式：`{"ts":"2026-07-19T...Z","stream":"stdout|stderr","line":"..."}`。

8. **`FrustrationState.kt`** — data class：`errorCount`, `lastErrorAt`, `repeatedCommandCount`, `lastSignature`, `lastCommandAt`, `score`, `lastTriggerAt`。

9. **`FrustrationTracker.kt`** — `@Component`，用 Caffeine `expireAfterAccess(30min)`（评审缺口 5 修复）。
   - key = `lab_session_id`（WS 握手提供）；若缺失则 fallback `containerName:user_id`。
   - `observeError(sessionKey, errorSlice, exitCode)`：解析 signature（轻量 regex，与 `docker_tools.py._ERROR_PATTERNS` 对齐），+1 分；同 signature 60s 内重复 +2。
   - `observeCommand(sessionKey, normalizedCmd, exitCode)`：非零 exit +1；5 分钟窗口内同一 normalizedCmd 3+ 次 +1。
   - `score(sessionKey): Int`。
   - `tryTrigger(sessionKey): FrustrationSignal?`：`score >= threshold(3)` 且距上次触发 > `cooldown(90s)` → 构造信号并清零 score；否则返回 null。
   - 阈值/冷却全部从 `seclab.frustration.*` 配置注入。

10. **`GuidanceSignal.kt`** — data class，**字段（评审 Q1 补全）**：
    ```kotlin

        val request_id: String,         // 与 signal_id 同源，便于追踪
    ```

### 1.3 双摄入路径去重（评审缺口 8）

- **WS TTY 流** = 低延迟触发源（毫秒级，用于挫败指数实时计算）。

## Phase 2 — ai-agent-service (Python) FastAPI 信号中枢

### 2.1 新增文件

目录：`d:\SecLab\SecLab\seclab-backend\ai-agent-service\`

1. **`guidance_service.py`** — 核心业务逻辑。
   - `class GuidanceSignal(BaseModel)`：字段对齐 Kotlin 侧 `GuidanceSignal` data class。
   - `class GuidanceAlertEvent(BaseModel)`：推给前端的事件 `{lab_session_id, conversation_id, message_id, content, error_excerpt, frustration_score, triggered_at}`。
   - `async def handle_guidance_signal(signal: GuidanceSignal) -> AsyncIterator[str]`：
     1. **幂等去重**：用 `signal.signal_id` 查 `ai_context_injection`（context_type='guidance-signal'）若已存在则直接返回缓存的 `conversation_id`，跳过 Dify 调用。
     2. **错误分类与落库**：调 `error_repository.classify_error_excerpt(signal.error_slice, exit_code=signal.exit_code)` 得到 signature/category/severity，再调 `save_error_event()` 落 `error_event` + 镜像 `learning_event`（评审 Q4：Python 统一分类）。
     3. **命令落库**：若 `recent_commands` 非空，逐条调 `container_command_repository.save_container_command_event()`，`source='tty_observer'`。
     4. **会话复用**：调 `ai_repository.ensure_guidance_conversation(lab_session_id, context, source='guidance-proactive')`（新函数，评审 Q3 修复）。`conversation_id` 形如 `guidance-{lab_session_id}`，按 `lab_session_id + source` 查找，**不**侵入 `dify_conversation_id` UNIQUE 约束。
     5. **组装 Dify inputs**：`{lab_task_summary, error_slice, error_signature, error_category, recent_commands, container_name, lab_key, frustration_score, trigger_reason, locale}` —— 这些是 Dify 云端 RAG 的检索键。
     6. **构造 query**（中文启发式提示词模板，不要直接给答案）：
        ```
        学生在 {{lab_key}} 实验中触发挫败指数 {{frustration_score}}（{{trigger_reason}}）。
        最近错误：{{error_slice}}
        最近命令：{{recent_commands | join("; ")}}
        当前任务：{{lab_task_summary}}
        请基于安全知识库给出 3 句以内的启发式提示，引导学生自己定位问题，禁止直接给 flag 或完整 payload。
        ```
     7. **流式调 Dify**：复用 `main.py` `/api/chat` 内的 httpx 流式逻辑，POST `${DIFY_API_URL}/chat-messages`，`response_mode=streaming`，body `{query, conversation_id: signal.dify_conversation_id or "", user: f"student-{signal.user_id}", inputs}`。
     8. **逐事件转发**：对 Dify 返回的每个 SSE 事件，原样 re-emit 给调用方，但额外包一层 `event: guidance_alert` + `data: {...}`，让前端能区分。
     9. **服务端持久化**（评审缺口 2：guidance 路径走服务端持久化，与 `/api/chat` 不对称但合理）：
        - 收到 `message_end` 时调 `update_conversation_after_stream(dify_conversation_id=...)` 回填真实 Dify 会话 id。
        - 调 `save_ai_message(role='assistant', content=full_reply, contains_context=True, raw_payload={...})`。
        - 调 `save_context_injection(context_type='guidance-signal', raw_context=signal.dict())`。
     10. **同时广播**：调用 `guidance_stream_registry.broadcast(lab_session_id, alert_event)`，让所有订阅 `GET /api/guidance/stream/{lab_session_id}` 的前端 SSE 收到推送。

2. **`guidance_stream_registry.py`** — `asyncio.Queue` 字典（评审缺口 14：单 worker 部署约束；多 worker 需替换 Redis pubsub，文档标注）。
   - `_queues: dict[str, set[asyncio.Queue]]`
   - `register(lab_session_id) -> Queue` / `unregister(lab_session_id, queue)` / `broadcast(lab_session_id, event)`。

3. **`test_guidance_service.py`** — 单测，mock httpx + 各 repository 函数。参考 `test_teacher_ai_analysis_service.py` 风格。

## 剩余风险与需用户确认事项

1. **多 worker 部署**：当前 `main.py` 用 `uvicorn.reload=True` 单 worker。若生产用 `gunicorn -w 4`，`guidance_stream_registry` 的 in-process Queue 会跨 worker 失效。**默认按单 worker 部署约束**，多 worker 需后续替换为 Redis pubsub（已在代码留 TODO）。
2. **Dify RAG 知识库内容**：云端 RAG 已由用户配置，本方案只负责把 `error_slice`/`lab_key` 等通过 `inputs` 字段传入，**不负责**安全知识库的内容维护。
3. **lab_task_summary 内容来源**：当前从 `lab_key` 反查一个静态任务摘要（写在 `LabAllowlist` 或配置里）。若需要动态从 `experiment-module-service` 拉取，需额外接口调用，本方案先用静态摘要，后续可扩展。
4. **挫败指数阈值调参**：`threshold=3`、`cooldown=90s`、`repeat-window=300s` 是初始值，需基于真实学生数据调参。建议先以宽松阈值上线，观察 1-2 周后再收紧。
5. **WS TTY 鉴权**：当前 WS 端点仅校验 `containerName ∈ LabAllowlist`，不校验 `user_id` 真实性。若部署在公网，需补 token 校验。本地/内网部署可接受。
