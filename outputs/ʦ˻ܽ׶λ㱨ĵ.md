# SecLab 教师端画像功能阶段汇报文档

汇报日期：2026-07-10

## 一、阶段工作背景

本阶段主要围绕 SecLab 平台的教师端画像功能进行完善，重点解决教师查看班级情况、查看学生个人画像、获取教学干预建议时存在的口径不清、展示不稳定、建议内容空泛等问题。

原有功能已经具备一定的数据展示能力，但教师端仍存在几个明显问题：

- 学生个人画像和班级画像的分析口径容易混在一起。
- 页面上存在英文技术字段、数据库表名或乱码班级名，不适合教师端直接使用。
- “推荐补强”类文案更像学生端训练推荐，不符合教师查看学生发展情况的场景。
- 建议内容偏模板化，缺少具体教学动作。
- AI 分析能力没有清晰区分前端、后端和 Dify 的职责边界。

因此，本阶段的目标是把教师端画像功能从“数据展示”进一步推进到“面向教师教学决策的分析辅助”。

## 二、本阶段已经完成的工作

### 1. 完成教师端学生个人画像页面修复

学生个人画像详情页已经调整为教师视角，页面重点展示当前学生的个人发展情况，包括：

- 总体画像分。
- 五维画像分。
- 最近训练作答。
- 个人画像摘要。
- AI 个人教学干预建议。

同时完成了页面中文化清理，去掉了教师端可见的英文技术字段，例如：

- `student_profile_snapshot`
- `Dashboard`
- `generated_question`
- `generated_question_attempt`

学生个人页现在只分析当前学生个人情况，不再混入班级平均分、班级共性薄弱点或班级教学建议。

### 2. 完成学生个人 AI 教学干预建议接口

新增学生个人 AI 分析接口：

```http
POST /api/teacher/students/{user_id}/profile/ai-analysis
```

该接口由后端调用 Dify API，前端不直接调用 Dify，也不暴露 API Key。

学生个人 AI 分析的数据来源限定为：

- 当前学生个人画像分数。
- 当前学生最近训练作答。
- 当前学生活跃统计。
- 当前学生个人错误、求助或 AI 使用记录。

AI 返回内容会经过后端校验，包括：

- JSON 格式校验。
- 必要字段校验。
- 学生端口吻拦截。
- 空泛建议拦截。
- 无效维度拦截。

如果 Dify 不可用、余额不足、超时或返回无效内容，系统会自动进入规则兜底，保证教师端页面仍然可用。

### 3. 完成教师端班级画像页面修复

班级管理与学生画像页面已经调整为班级层分析，重点展示：

- 班级列表。
- 学生数。
- 活跃人数。
- 班级画像均分。
- 班级训练均分。
- 班级薄弱维度。
- 学生画像列表。

同时修复了班级名显示问题：

- `????` 不再直接显示。
- 空班级名会显示为 `未命名班级 {classId}`。
- 部分英文种子班级名已经映射为中文班级名。

### 4. 完成班级 AI 教学安排建议接口

新增班级 AI 分析接口：

```http
POST /api/teacher/classes/{class_id}/ai-analysis
```

班级页现在不再只依赖前端规则模板，而是通过后端接口调用 Dify 生成班级教学建议。

班级 AI 建议的输出结构包括：

- 薄弱维度。
- 影响人数。
- 证据依据。
- 课上教学动作。
- 课后跟进动作。
- 优先级。

这样可以让教师看到更接近实际教学安排的建议，而不是单纯的“建议加强训练”。

### 5. 完成班级与学生个人分析分层

目前已经明确区分：

学生个人页：

- 关注单个学生的发展情况。
- 输出个人干预建议。
- 不出现班级整体结论。

班级页：

- 关注班级整体画像。
- 输出班级共性关注和班级教学安排建议。
- 不输出单个学生个人干预建议。

这个分层是本阶段非常重要的修复点，因为它决定了教师端画像功能是否符合真实教学场景。

### 6. 完成 Dify 后端接入与兜底机制

Dify 接入方式已经调整为后端调用：

```env
DIFY_API_URL
DIFY_API_KEY
```

前端不会出现：

- Dify API Key。
- embed token。
- Dify 聊天气泡脚本。
- Dify 原始错误。

后端优先使用 Dify `blocking` 模式。如果当前 Dify Agent App 不支持 `blocking`，后端会自动降级为 `streaming`，并拼接 streaming 返回中的 answer 内容。

如果 Dify 调用失败，系统会返回规则兜底建议，保证教师端功能不中断。

### 7. 完成基础测试与构建验证

后端已执行：

```powershell
python -m unittest test_teacher_repository_helpers.py test_teacher_ai_analysis_service.py
python -m py_compile main.py teacher_repository.py teacher_ai_analysis_service.py teacher_ai_prompts.py
```

前端已执行：

```powershell
npm run vue-tsc
npm run build
```

目前相关测试、类型检查和构建均已通过。

## 三、本阶段遇到的主要困难

### 1. 教师端和学生端口径容易混淆

最开始页面中的“推荐补强”更像学生端训练推荐，例如让学生继续训练、补强某类题目。但教师端的真实需求不是直接给学生布置一句训练建议，而是帮助教师判断：

- 这个学生哪里需要关注。
- 为什么需要关注。
- 教师可以采取什么教学动作。
- 是否需要课上讲评、个人复盘或课后跟进。

因此，本阶段花了较多精力重新梳理教师端表达方式，把学生端口吻改成教师端口吻。

### 2. 班级画像和学生个人画像边界不清

原有页面中班级层和学生层容易混用，例如在学生个人页中出现班级性质的建议，或者班级页建议过于像单个学生训练建议。

本阶段重新划分了两层：

- 学生个人页只看个人。
- 班级页只看班级共性。

这个调整涉及前端页面、后端接口、数据输入和 AI Prompt，多处都需要保持一致。

### 3. Dify 应用类型与调用方式存在差异

后端最初按同步 `blocking` 模式调用 Dify，但实际测试时发现当前 Dify Agent App 返回：

```text
Agent Chat App does not support blocking mode
```

也就是说，当前 Dify 应用类型不支持 blocking 模式。为了解决这个问题，后端增加了兼容逻辑：

- 优先尝试 blocking。
- 如果明确不支持 blocking，则自动切换为 streaming。
- 在后端解析 streaming 中的 answer 内容。

这样可以兼容当前 Dify 应用，也能保留后端统一调用的架构。

### 4. Dify 余额或模型调用能力会影响真实 AI 结果

当前代码层面已经接好 Dify，但真实调用时还受到 Dify 账号余额、模型配置、应用类型等外部因素影响。

在余额不足时，后端会正常返回规则兜底建议，但无法验收到真实 LLM 生成结果。

这属于外部服务依赖问题，不影响页面基础可用性，但会影响 AI 建议质量验收。

### 5. 页面可见文案需要逐处清理

教师端页面此前存在一些英文技术字段、内部事件名、数据库表名或乱码。这些问题不是单个组件的问题，而是分散在多个页面和后端返回字段中。

本阶段已经清理了主要页面，但后续仍需要通过浏览器逐页验收，确保没有遗漏。

## 四、目前仍然需要的支持或后续工作

### 1. 需要确认 Dify 账号和模型可用

目前后端已经完成 Dify 接入，但真实 AI 结果依赖 Dify 侧：

- API Key 是否正确。
- Dify 应用是否可用。
- 模型余额是否充足。
- 模型是否能稳定返回严格 JSON。

后续需要在 Dify 可用后重新验收：

- 学生个人 AI 建议是否能真实返回。
- 班级 AI 教学安排建议是否能真实返回。
- 返回内容是否符合教师端语气和教学场景。

### 2. 需要做一次浏览器端人工验收

虽然前端类型检查和构建已经通过，但仍建议进行页面级验收：

- 教师首页是否无英文技术字段。
- 班级页是否能正常切换班级。
- 班级 AI 建议是否能展示课上与课后动作。
- 学生个人页是否只展示个人建议。
- Dify 不可用时兜底提示是否正常。
- 页面是否还有 `undefined`、`null`、`????` 等异常文本。

### 3. 需要继续优化 AI Prompt

当前 Prompt 已经能约束输出结构，但真实效果还需要根据 Dify 返回结果继续微调。

后续重点是让 AI 建议更像教师可执行的教学安排，例如：

- 更具体的课堂活动。
- 更具体的复盘要求。
- 更明确的观察点。
- 更合理的优先级。

### 4. 可以继续补充更多过程数据

目前学生个人 AI 输入已经加入：

- 最近训练作答。
- 个人错误事件。
- 求助记录。
- AI 使用记录。

后续如果需要更精准的画像，可以继续补充：

- 实验耗时。
- 提示请求次数。
- 重复提交失败次数。
- 容器命令错误类型。
- 课程模块完成情况。

这些数据可以让 AI 建议更贴近学生真实学习过程。

### 5. 需要确认数据库初始化脚本和演示数据

部分班级名、示例训练题和种子数据已经做过中文化处理。后续如果要部署或演示，需要确认：

- 初始化 SQL 是否同步最新字段。
- 演示班级名是否正常。
- 演示学生是否有足够画像数据。
- 演示训练记录是否能支撑页面展示。

## 五、当前阶段成果总结

本阶段已经完成的核心成果可以概括为三点：

第一，教师端画像功能完成了“班级层”和“个人层”的分离。

教师现在可以在班级页查看班级共性问题，在学生个人页查看单个学生的发展情况，不会再把两种分析混在一起。

第二，AI 分析能力已经通过后端接入 Dify。

前端不直接接触 Dify，也不暴露 API Key。后端统一负责 Prompt 构造、Dify 调用、JSON 校验、异常兜底和结果返回。

第三，教师端建议从“空泛补强”升级为“教学动作建议”。

学生个人建议强调个人复盘、错误定位、AI 交互检查等动作；班级建议强调课上讲评、随堂检查、课后跟进等教学安排。

## 六、下一步计划

下一步建议按以下顺序推进：

1. 先确认 Dify 账号余额和模型配置，保证 AI 能真实返回。
2. 做一次完整浏览器验收，覆盖教师首页、班级页、学生个人页。
3. 根据真实 AI 输出继续调整 Prompt。
4. 补充更多学习过程数据，让画像建议更精准。
5. 整理一套稳定演示数据，方便后续向老师展示完整流程。

## 七、需要老师确认的问题

后续可以请老师重点确认以下方向：

1. 教师端画像分析的五个维度是否符合课程教学目标。
2. 班级教学建议是否更关注课上讲评，还是更关注课后作业和复盘。
3. 学生个人干预建议是否需要区分不同严重程度。
4. AI 生成建议是否需要保留教师审核或编辑入口。
5. 后续是否需要把画像结果导出为报告或作为课程评价依据。
